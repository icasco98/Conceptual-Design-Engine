Connected is not clean — but it's less far from clean

Batch 002 made every room touch and get a real door; the clean rate (zero hard problems) stayed at 0 of 56 scenarios anyway. This batch's hypothesis: the bubble stage that decides where rooms go has no repulsion for pairs that should stay apart, no notion of the public-to-private gradient, and no awareness of which rooms need a real exterior wall — so the search inherits a starting point that already fights three of the rule set's own checks before it even begins. Tasks 2–4 — three additions to the topology and dimensioning stages

geometry/topology.ts, scenarios.ts

All three are optional fields on TopologyRoom (tier, isEntryPoint, needsExterior), populated by scenarios.ts from exactly the same rooms.ts facts every other check already reads (tierOf, sleepingOf) — an existing caller or test that never sets them gets batch 002's behaviour back unchanged.

TASK 2Extra repulsion for undesired pairs — buildUndesiredPairs

Every instance-to-instance pair whose types are marked undesired now gets a repulsion term on top of the generic one every pair already gets in the bubble simulation — the generic term alone treated an undesired pair exactly like any two unrelated rooms of the same size, which is the gap batch 002 left behind. Deliberately a full cross product of instances, not buildEdges' cycled one-to-one: checkAdjacency's own undesired check fails the whole row the moment any instance of one type touches any instance of the other, so three bedrooms and one kitchen means three pairs kept apart, not a stand-in single pair. Unit-tested directly: an undesired pair settles farther apart than an unrelated pair of the same sizes, and gets no attraction (only the new repulsion boost) from an undesired-only row.

Measured in isolation (Tasks 3 and 4 held back), this repulsion boost alone nets worse across the 56-scenario suite than batch 002 (mean hard problems 16.92 vs. 16.36) — pushing undesired pairs apart disrupts the bubble diagram's overall coherence in ways that cost more in reachability than they save in adjacency. Only the full combination of Tasks 2, 3 and 4 together recovers a real, net improvement (see "Why one commit, not three," below).

TASK 3A privacy-tier bias toward/away from the entry point

Public-tier rooms (entry, living, dining, a diwaniya) are pulled toward the entry point each iteration; private-tier rooms (bedrooms) are pushed away — both as a spring proportional to the room's current distance from the entry, so the bias scales with how far off a room already is rather than applying one fixed nudge regardless of position. Semi-public and tier-exempt rooms (a hallway, a bathroom, a garage) get no bias either way — there is no single "correct" direction for a room the tier check itself never judges. Inert whenever no room in the program declares itself the entry point, which is also what keeps every existing caller and test that never sets isEntryPoint completely unaffected. Unit-tested: given an entry, a public room and a private room, the private room settles farther from the entry than the public one does; a program with no entry point produces bit-for-bit the same bubble layout as before this task existed.

TASK 4A boundary-touch repair pass in dimensionRooms

After the slice-and-dice partition runs exactly as batch 002 built it, a second pass identifies any room flagged needsExterior (rooms.ts's own sleeping fact — a bedroom, a driver's or nanny's room) that landed on a fully interior slice, and swaps it — by rectangle assignment, never by moving a rectangle — for the closest-area available slice that does touch the plot boundary. This is deliberately a swap, not a re-partition: the set of rectangles in the partition never changes, only which room-id points at which one, so whatever was already true of the partition (exact tiling, zero overlap, by construction) is still true afterward, unconditionally. Closest-area rather than first-found, so a bedroom doesn't trade its unmet exterior wall for a closet-sized corner it now has to fight its way back up from. A room with no available trade is left unmet rather than forced — the same "flagged, never forced" rule the interactive editor's own plot boundary has kept since the first version of this tool. Unit-tested with an explicit 12-room grid engineered to leave at least one fully interior leaf: flagging that room needsExterior moves it onto a boundary-touching slice, and the swap is checked to still tile the boundary exactly with zero overlap afterward.

This is the cleanest single win in the batch: windowless sleeping rooms went from 22 instances (13 scenarios) to zero, across the whole 56-scenario suite. A room-assignment swap that can never break the underlying partition's own safety guarantee turned out to be enough to eliminate an entire hard-problem category.

Why one commit, not three

The batch's usual convention is a small, separate commit per task. This batch's own numbers said not to follow it here: Task 2 alone regresses the suite (see its own note above), and only the full combination of Tasks 2–4 together nets an improvement. Committing Task 2 by itself would have meant landing a genuine regression — or dishonestly lowering the regression baseline to permit one — purely to preserve commit granularity. The three were measured together, committed together, and the commit message says exactly this.

Task 5 — squarified treemap: skipped, and why

SKIPPED Slice-and-dice was chosen in batch 002 specifically because its non-overlap and boundary-fit guarantees hold by construction, with nothing to verify afterward — every recursive split exactly tiles its own rectangle, full stop. A squarified treemap produces better-proportioned rectangles (fewer thin slivers, which is exactly what trips the batch-001 3:1 aspect-ratio rule), but it needs its own argument for why it still guarantees that same non-overlap and boundary-fit property, and this batch did not develop enough confidence in that argument to risk trading a correctness guarantee for a shape improvement. Task 4's own boundary-repair pass leans directly on slice-and-dice's "exact tiling by construction" property for its own safety argument (see Task 4, above) — a squarified variant would need that reworked too, not just the partition itself. Skipped plainly rather than attempted under time pressure with a weaker guarantee than what is already there.

Honest limits of this batch

  • Reachability is untouched, and it's the biggest category there is. 556 findings across all 56 scenarios before this batch, 573 after — essentially flat, slightly worse in raw count. Nothing in this batch gives the topology stage any notion of a circulation backbone; it only biases which rooms end up near which other rooms, not whether a passable path threads them all together.
  • The clean rate moved from 0% to 3.6%, not to anything close to the whole suite. Two scenarios reaching zero hard problems is real progress and not nothing, but "connected and now less conflicted" is still a long way from "clean."
  • Squarified treemap was not attempted (Task 5). Deliberately, for the reason given above — not for lack of time to try, but for lack of confidence in preserving slice-and-dice's own safety guarantee.
  • Doorway clearance got measurably worse (4 → 14 instances). Not investigated further this batch; worth a look before assuming it's noise.
  • The tuning win (Task 6) is smaller and secondary to the topology change. 15.819 vs. 16.123 mean hard problems is a real but modest improvement on top of what Tasks 2–4 already did, and it is measured on a feasible subset at 150 iterations, not the full 56-scenario suite at 400 — not directly comparable to this report's own headline 16.36 → 14.65 figure.

What batch 4 should focus on

Reachability, not another topology bias. Task 1's own diagnosis is unambiguous: reachability findings (556, then 573) outnumber every other hard-problem category by more than five to one and touch every single scenario in the suite, both before and after this batch's work. Nothing this batch built addresses it, because nothing in the topology or dimensioning stages currently models circulation at all — the bubble diagram pulls related rooms together and now pushes conflicting ones apart and biases by privacy tier, but it has no concept of a hallway needing to actually reach every room, or of a "through_room" problem (433 of the 556 instances) where a route exists only through a room nobody should have to walk through. A plausible next step in the same spirit as this batch's own diagnose-first approach: have the topology stage treat passable rooms (entry, hallway, mudroom, stair) as a backbone the bubble diagram tries to keep central and well-connected to everything else, rather than treating every room as an equal node in one undifferentiated graph. This is a real, separate piece of research and design work, not a small addition — which is exactly why it deserves its own batch rather than a rushed sixth task bolted onto this one.

Second, smaller: look at why doorway clearance got worse. Four instances became fourteen. Not investigated here, but cheap to check first: is a specific one of Tasks 2–4's new forces pushing two doors toward the same wall more often, or is it an artifact of the search's random walk taking different paths through different starting geometry, the same explanation that covers the 14 scenarios that regressed overall.

Not recommended for batch 4, same reasoning as batch 002's own report gave: the Obsidian-style interactive graph visualization the owner wants eventually. Still a viewer for a graph this pipeline already computes internally and discards, better built once the placement pipeline (topology and circulation) is more settled than it is today.
